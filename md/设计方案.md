## 一、前期调研

### 1.1 业务背景

电商平台每天产生海量用户行为日志（页面访问、点击、支付、错误等），这些日志蕴含着巨大的业务价值：

- **运营团队**：需要了解用户行为模式，优化产品体验
- **技术团队**：需要快速定位系统异常和错误
- **管理层**：需要数据支撑业务决策

传统日志处理方式面临以下痛点：

| 痛点          | 说明                                  |
|:----------- |:----------------------------------- |
| **查询门槛高**   | 需要掌握 Elasticsearch DSL 或 SQL 才能查询数据 |
| **分析效率低**   | 数据查到后还要人工分析，缺乏自动洞察                  |
| **响应速度慢**   | 从发现问题到定位根因，周期过长                     |
| **AI 能力缺失** | 没有利用大语言模型降低使用门槛                     |

### 1.2 竞品 / 方案调研

| 方案                                                | 优势                         | 劣势                      |
|:------------------------------------------------- |:-------------------------- |:----------------------- |
| **ELK Stack** (Elasticsearch + Logstash + Kibana) | 日志处理行业标准，功能全面              | 查询需掌握 DSL，学习成本高，无 AI 能力 |
| **Splunk**                                        | 企业级日志分析平台，搜索能力强            | 商业软件，价格昂贵，中小团队用不起       |
| **Datadog**                                       | SaaS 化运维监控，开箱即用            | 成本高，数据离岸，定制化受限          |
| **Grafana Loki**                                  | 轻量级，与 Prometheus 集成好       | 功能相对简单，分析能力弱            |
| **本方案**                                           | **LLM 驱动的自然语言查询 + 自动分析洞察** | 依赖 LLM 接口，有网络延迟         |

### 1.3 技术调研

| 调研项            | 结论                                                 |
|:-------------- |:-------------------------------------------------- |
| LLM 生成 DSL 可行性 | DeepSeek API 能稳定生成 ES 查询 DSL，中文理解能力强               |
| 异步 AI 分析架构     | Spring @Async + 缓存，搜索与分析解耦，用户体验好                   |
| ES 聚合分析能力      | 支持 terms / date_histogram / value_count 等多种聚合，满足需求 |

## 二、设计思路

### 2.1 核心设计原则

```
🧠 智能 — AI 驱动，自然语言交互，降低使用门槛
⚡ 高效 — 搜索与分析异步解耦，秒级响应
📊 直观 — 数据可视化，图表 + 表格 + 文本洞察三位一体
🔧 可扩展 — 模块化设计，支持接入更多分析模板和 AI 能力
```

### 2.2 关键设计决策

| 决策              | 方案                         | 理由                                   |
|:--------------- |:-------------------------- |:------------------------------------ |
| **搜索与分析分离**     | 搜索同步返回，AI 分析异步缓存           | 搜索必须快（1-2秒），AI 分析可以慢（3-5秒），两者解耦不互相阻塞 |
| **异步任务自调用**     | `@Lazy` 自注入 + `@Async`     | 解决 Spring 代理自调用失效问题，确保异步真正生效         |
| **DSL 校验 + 修复** | DslValidator 自动修复字段名和查询类型  | 避免 LLM 生成的 DSL 语法错误导致 ES 查询失败        |
| **连接池管理**       | HttpClient 连接池（20连接/10每路由） | 防止批量请求时连接耗尽导致服务崩溃                    |
| **缓存过期清理**      | 每次新搜索自动清理旧分析缓存             | 保证内存不泄漏，用户未点击的分析自动释放                 |

### 数据流

```
① 用户输入自然语言问题
       │
② LLM 生成 ES 查询 DSL（DeepSeek API）
       │
③ DslValidator 校验 + 修复 DSL
       │
④ 注入分页参数 → 发送到 ES
       │
⑤ ES 执行查询 → 返回聚合 + 日志数据
       │
⑥ 构建响应 → 返回前端（含 analysisTaskId）
       │  ← 用户看到结果
⑦ 后台异步启动 AI 数据分析（LLM）
       │  ← 缓存分析结果
⑧ 用户点击"AI分析" → 轮询获取缓存结果
```

## 四、核心流程设计

### 4.1 自然语言 → DSL 转换

```
"过去24小时访问量最高的页面"

  │ LLM 理解意图
  ▼

{
  "size": 0,
  "query": {
    "bool": {
      "filter": [{"range": {"timestamp": {"gte": "now-24h"}}}]
    }
  },
  "aggs": {
    "top_pages": {
      "terms": {"field": "page", "size": 10, "order": {"_count": "desc"}}
    }
  }
}
  │ DslValidator 校验
  │ - 去除 markdown 代码块标记
  │ - 检查危险操作（delete/update）
  │ - 修复 keyword 字段名
  │ - 修复 match 查询（error_msg → error_msg.keyword）
  │ - 限制 size ≤ 100
  ▼

✅ 安全、合法的 DSL → 发送 ES
```

### 4.2 搜索与 AI 分析异步解耦

```
时间线:

用户请求 ──┬──→ ② LLM生成DSL（同步）
           │
           ├──→ ③ ES查询（同步）
           │
           ├──→ ④ 返回结果 ←── 用户看到数据（~1.5秒）
           │
           └──→ ⑤ 提交异步分析任务（不阻塞）
                    │
                    ├──→ ⑥ LLM分析数据摘要（异步线程）
                    │
                    └──→ ⑦ 缓存分析结果

用户点击"AI分析" → ⑧ 轮询缓存 → 展示分析报告
用户未点击 → 下次搜索自动清理缓存
```

### 4.3 异常处理策略

| 异常场景         | 处理方式                          |
|:------------ |:----------------------------- |
| LLM API 调用失败 | 返回错误提示，不阻塞前端                  |
| DSL 解析失败     | DslValidator 返回 null，提示用户换种说法 |
| ES 查询异常      | 捕获异常，返回 500 + 友好提示            |
| 异步分析异常       | try-catch 隔离，不影响搜索主流程         |
| 连接池耗尽        | 阻塞等待，不崩溃（CallerRunsPolicy）    |

## 五、选型依据

### 5.1 后端：Spring Boot 2.7.18

| 维度        | 评估                               |
|:--------- |:-------------------------------- |
| **生态成熟度** | Java 生态最主流的微服务框架，社区活跃            |
| **开发效率**  | 注解驱动开发，内嵌 Tomcat，零配置部署           |
| **异步支持**  | `@Async` + `@EnableAsync` 原生异步支持 |
| **团队熟悉度** | Java 8 + Spring Boot 是实习生最熟悉的技术栈 |
| **版本选择**  | 2.7.x 是 2.x 最终稳定版，兼容 Java 8      |

### 5.2 LLM：DeepSeek API

| 维度       | 评估                                 |
|:-------- |:---------------------------------- |
| **中文理解** | 中文能力优于同级别模型，准确理解复杂业务描述             |
| **代码生成** | 在代码生成 benchmark 上表现优秀，ES DSL 生成质量高 |
| **性价比**  | 价格远低于 GPT-4，适合高频调用场景               |
| **兼容性**  | 兼容 OpenAI API 格式，迁移成本低             |
| **响应速度** | 推理速度快，平均 1-3 秒返回结果                 |

### 5.3 搜索引擎：Elasticsearch

| 维度       | 评估                                            |
|:-------- |:--------------------------------------------- |
| **日志场景** | 日志分析的行业标准方案，天然适合全文搜索和聚合                       |
| **聚合分析** | 支持 terms / date_histogram / value_count 等多种聚合 |
| **查询语言** | 提供强大的 DSL，也支持通过 LLM 生成                        |
| **扩展性**  | 水平扩展，分片机制支持 PB 级数据                            |

### 5.4 前端：Vue 3 + Element Plus + ECharts

| 技术               | 选型理由                             |
|:---------------- |:-------------------------------- |
| **Vue 3**        | 国内最流行的前端框架，组合式 API 更简洁           |
| **Element Plus** | Vue 3 生态最成熟的 UI 组件库，表格/分页/按钮开箱即用 |
| **ECharts**      | 百度开源可视化库，图表类型丰富，文档完善             |

## 七、Demo 演示方案

### 7.1 演示流程（5分钟）

```
1️⃣ 进入系统（30秒）
   → 展示界面布局：搜索框、快速示例、待分析区域

2️⃣ 基本搜索（1分钟）
   → 点击"过去24小时各设备类型分布"
   → 展示：饼图（设备占比）+ 日志明细表格 + 分页

3️⃣ 趋势分析（1分钟）
   → 搜索"今天每小时的页面访问趋势"
   → 展示：折线图（时间趋势）+ 自动识别的图表类型

4️⃣ AI 智能分析（1.5分钟）
   → 在搜索结果页点击"开始AI分析"按钮
   → 展示：轮询等待 → AI 自动生成数据洞察报告
   → 强调：异步架构、搜索与分析解耦

5️⃣ 错误分析（1分钟）
   → 搜索"过去24小时支付失败最多的错误信息"
   → 展示：聚合 + AI 分析建议
```

### 7.2 需要强调的技术亮点

| 亮点            | 话术                                        |
|:------------- |:----------------------------------------- |
| **LLM + DSL** | "用 DeepSeek 将自然语言转为 ES 查询 DSL，非技术人员也能查数据" |
| **异步 AI 分析**  | "搜索与 AI 分析异步解耦，用户先看到数据再决定是否要 AI 分析"       |
| **DSL 安全校验**  | "LLM 生成的 DSL 经过多层校验，防止误操作和语法错误"           |
| **数据可视化**     | "系统自动判断数据特征，选择最合适的图表类型展示"                 |
